### Feature

**You own the design. Plan, review, verify.** Route implementation through the configured `feature` role and stay in the lead.

1. `how` over the affected subsystem.
2. `architect` for parallel design exploration. Skipping stays as `architect skipped: <reason>`; do not fold the design decision silently into implementation.
3. Write the throughput checkpoint as four todo items. A dimension that genuinely does not apply (single file, no fan-out) keeps its item with `n/a: <reason>` rather than being dropped:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target (the **separate-before-serializing-shared-state** principle skill). Serialize only for real invariants. This includes state on the user's machine that code you run but do not own writes or kills: pid files, data folders, caches, running app processes. Find it before the first run and give that code a private data folder. OS state keyed by an identifier the new code shares with an app the user runs (permission grants per bundle ID, a preferences domain, a process name, an install path) counts too. Give the new code its own identifier during development instead of guarding every command, and have tests stub any destructive command on that state. Ask before changing or deleting the user's live app data. Synthetic input (posted key or mouse events, or taking focus) lands in the user's frontmost app. Tell the user before the first run, pick events no running app reacts to, and record which events reached the frontmost app. If the runs need the user to stay off the machine, say how long at plan time and get agreement before building. A failed run is the harness's fault, not the user's activity. After any run that posts modifier keys, read `CGEventSource.flagsState(.hidSystemState)` and confirm that no modifier is still held. Treat it as teardown, like processes and temp folders, and tell the user before posting events to clear one.
   - **Smallest safe decomposition.** Name the smallest independently verifiable semantic units; do not translate them into a worker count.
4. Turn implementation slices into semantic work units and dispatch them as `feature` through [`HOST-COMPATIBILITY.md`](../../../agent-mode/HOST-COMPATIBILITY.md). Give each unit file paths, the named data shape and organizing structure from **principle-model-the-domain**, and success criteria. The profile decides whether the coordinator or workers execute them. Review every returned diff. When implementation admits genuinely competing shapes, use **arena**; its own configured routes control the comparison. Comments per **Comments**. For upstream-derived files, re-ground against the source. Port shared-primitive improvements to every consumer and verify each.
5. Verify on the matching surface. "Inconclusive" or wrong-surface is not a pass; flag it. A blank or missing measured value (an exit code, a count, a timing) is a failed check. Read exit codes with the running shell's syntax, or run the check under `bash`. Size test inputs and fixtures from the code's thresholds, not the spec's wording, and name the behaviors no input can trigger. The thresholds include those of any library the change wraps. Read the library's own input checks and thrown errors, and give each one an outcome the user would expect, with a test, before you write a catch-all. A harness or script written to verify the change joins the standard check target, and its exceptions live in versioned data that names a decision ID, never in a command-line flag. A "no difference" result counts only after a planted difference surfaced through the same pipeline.
6. Build and verify small ordered units. Preserve that order in commits only when the user explicitly asks for them.
   Use the **sequence-verifiable-units** principle skill, verifying each small unit before the next.
7. If the design is contested, `interrogate` before implementation.
8. Finish with verified local changes. Leave publication to the user's explicit delivery request.

Code-coupled work stays one semantic unit unless it produces independently verifiable artifacts. Independent artifacts become separate units after blocking prerequisites finish. Worker count never follows from this decomposition; setup owns it. Rewrite the checkpoint at phase boundaries.

**Reply:** what you built, what you chose and why, open decisions. Tables for design alternatives. When the task comes from an issue or spec, give each acceptance criterion a status (met, open, or not applicable), and flag any checklist row whose verify method the work showed cannot cover it.
